# Commits, PRs, and merge policy

## Base branch

Base ref: `$(git symbolic-ref --short -q refs/remotes/origin/HEAD || echo origin/main)`. It falls back to `origin/main` when `origin/HEAD` is unset (a repo made with `git remote add`, not `git clone`). Each Bash call may run in a fresh shell, so never keep it in a variable: paste the substitution into the same command that uses it. Branch off, diff against, and open PRs to that ref; wherever a skill says `<base>`, use it.

## Worktrees

Look in the project root for an existing worktree folder (`.worktrees/`, `worktrees/`, or `.claude/worktrees/`) and use it. None: create `.worktrees/`. Put every worktree at `<folder>/<branch>`. Before adding one, make sure the folder is git-ignored: `git check-ignore -q <folder>/` (keep the trailing slash; without it a folder that does not exist yet reads as not ignored). If not, add `<folder>/` to `.gitignore` and commit that line on its own. Work only inside your own worktree.

Right after adding a worktree, run the repo's dependency install inside it (the package manager its lockfile names, or the setup command the repo documents) and stop if that fails. Never run a tool from, or against, the user's main checkout to get around a missing install. Why: a fresh worktree has no installed dependencies, so formatters, linters and type checkers fail or get skipped (lesson: okay-lessons#12).

## Commits

- One line. No body. No trailers (no Co-Authored-By).
- Follow the repo's existing style; otherwise `type: subject` (fix, feat, chore, docs, refactor, test, perf).
- Never force-push.

## PR / MR

- Title: `type: subject`, at most 70 characters.
- Body: English, at most 300 words, sections in this order: Problem / Cause / Change / Evidence / Not touched / Risks.
- Last line links the issue when one exists: `Closes #<n>` (GitHub) or `Fixes TON-<n>` (Linear; the Linear GitHub integration closes the issue on merge).
- No AI attribution anywhere: commits, PR bodies, comments, code. PR bodies and comments carry no AI footer (such as "Generated by ..."); if a tool adds one, edit the body or comment to remove it.
- Contributor mode uses its own MR description (see [contributor-mode.md](contributor-mode.md)).

## Merge policy

- Merge needs an allow rule for `gh pr merge` / `glab mr merge` (the auto-mode classifier refuses merges without one). Without that rule, stop at the approval and hand the merge to the user with the PR/MR link.
- When `gh pr merge` / `glab mr merge` cannot run (for example in a cloud session), the code host's REST API or MCP merge tool may do the merge, only with all three: an explicit title `<PR title> (#<n>)`, an explicit non-empty one-line body (the issue-closing line, such as `Closes #<n>`; no issue: one line saying what changed), and the expected head SHA. One of the three cannot be passed: hand the merge to the user.
  - Never send an empty message this way. Observed on GitHub: a squash merge through the MCP merge tool with an empty message fell back to the default body and added a `Co-authored-by` trailer. The same merge with the explicit title and the one-line body produced exactly that message, with no trailer.
  - Check the resulting commit message once per repo: `git fetch origin && git log -1 --format=%B <merge sha>`. Anything beyond the title and the one line: stop merging this way in that repo and hand merges to the user.
- Merge only when the PR head equals the SHA in the latest `APPROVED (round <n>) at <sha>` comment ([review.md](review.md)). A newer head needs a fresh check first. Pass that SHA to the merge so a late push makes it fail: `--match-head-commit <sha>` (`glab`: `--sha <sha>`).
- Squash merges through the CLI pass an explicit subject and an empty body, which drops the Co-authored-by and Claude-Session trailers the default body collects: `gh pr merge --squash --match-head-commit <sha> --subject "<PR title> (#<n>)" --body ""`.
- L1 with the allow rule: merge once the PR has the approval above and CI is green. Use `gh pr merge --auto` with the flags above (or `glab mr merge --auto-merge --squash --sha <sha>`). If auto-merge is disabled on the repo, wait with `gh pr checks --watch`, then merge. If the repo has no CI checks at all, run the full test suite locally, paste the result in the PR, and merge only if it passes.
- L2+: merge only after the user explicitly approves in the conversation, and only with the allow rule above. One exception: under an autonomy grant the merge goes ahead without that approval when every condition in [autonomy.md](autonomy.md) holds. The grant replaces the user's approval only; every other rule in this section stays. Before each merge, and again before each PR of a back-to-back batch:
  - The head contains the current base tip: `git fetch origin && git merge-base --is-ancestor <base> <head sha>`. If it does not, merge the base into the branch, push, and wait for CI and a fresh approval on the new head ([review.md](review.md)).
  - The required checks finished green, in the same command line as the merge: `gh pr checks <n> --required --watch --fail-fast && gh pr merge <n> ...` (drop `--required` when the repo marks no check as required). Never join the two with `;`, and never merge on a pending check.
  - Why: an approval and a green CI run count only for the base they ran on. "Mergeable" means no textual conflict, and an earlier merge in the same batch moves the base (lesson: okay-lessons#16).
- Pushing needs the user's OK unless the lane's merge policy already covers it (L1 with the allow rule does). One batch-level OK at the throughput checkpoint covers the pushes and PRs of every ticket in that batch; do not ask again per push. An autonomy grant covers the pushes and PRs of its scope ([autonomy.md](autonomy.md)).
- Contributor mode never merges; maintainers do.

## Attribution settings

Claude Code adds its own trailers and footers unless the repo's `.claude/settings.json` turns them off: an empty string hides each one, and `sessionUrl: false` drops the Claude-Session trailer and the PR session link. Cloud sessions read this file only in single-repo sessions, so the rules above apply either way.

```json
{
  "attribution": {
    "commit": "",
    "pr": "",
    "sessionUrl": false
  }
}
```

Merge the `attribution` key into an existing file and keep its other keys. The file must be tracked: if `.gitignore` ignores `.claude/`, replace that line with `.claude/*` and `!.claude/settings.json`.
